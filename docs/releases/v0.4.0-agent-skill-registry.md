# Release Notes — v0.4.0-agent-skill-registry

**Release date:** 2026-08-01
**Scope:** Agent routing infrastructure + DevOps expert

---

## 1. Overview

v0.4.0 introduces the **Agent Skill Registry**, a central, data-driven
routing system that maps expert *skills* to *specialist agents*. It
replaces the previously hardcoded `CATEGORY_KEYWORDS` dictionary in the
team coordinator as the source of truth for task classification, while
remaining fully backward compatible.

This release also brings the **DevOps Engineer Agent** (added in the
prior feature work) into the registry, making infrastructure / CI-CD
requests routable through the same mechanism as the existing security
experts.

### What changed at a glance

```
Before (v0.3.x)                          After (v0.4.0)
─────────────────────────                ─────────────────────────
Coordinator._classify()                  Coordinator._classify()
    │                                        │
    ▼                                        ▼
CATEGORY_KEYWORDS (hardcoded)          SkillRegistry.classify(text)
dict in coordinator.py                 │
                                          │
                                     skills/agent_skills.yaml
                                     (single source of truth)
```

## 2. New features

- **Central Skill Registry** — `agents/team/skill_registry.py` provides
  `SkillDefinition`, `SkillRegistry`, and a `load_skill_registry()`
  factory for reading the central definition file.
- **Data-driven skill definitions** — `skills/agent_skills.yaml` defines
  each skill with `name`, `category`, `agent`, `prompt`, `keywords`,
  `capabilities`, `version`, and `enabled`.
- **Keyword classification engine** — `SkillRegistry.classify(text)`
  scores a task across categories (each keyword match contributes +2.0,
  normalized to weights, with a `general` fallback). Disabled skills
  (`enabled: false`) are excluded from routing.
- **Lazy agent instantiation** — `SkillRegistry.load_agent(category)`
  builds a specialist instance from its import path (`module:Class`)
  without hard imports, avoiding circular dependencies.
- **Runtime toggling** — `set_enabled(category, bool)` turns routing on
  or off per skill without editing source.
- **Live agent adoption** — `register_agent(instance)` syncs a registered
  specialist's capabilities into the registry while preserving configured
  keywords.
- **Coordinator integration** — `CoordinatorAgent` accepts an optional
  `skill_registry` constructor parameter; `_classify()` delegates to the
  registry. New `skill_registry` property exposes it.
- **DevOps Engineer Agent** — `DevOpsAgent` (category `devops`) with
  Docker, Docker Compose, Kubernetes, CI/CD, GitHub Actions, Jenkins,
  Terraform, Ansible, IaC, cloud deployment, monitoring/logging, and
  secure-DevOps capabilities, fully routable via the registry.
- **New exports** — `SkillRegistry`, `SkillDefinition`, and
  `load_skill_registry` exported from `agents.team`.

## 3. Architecture changes

### Routing pipeline

```
User Request
    |
CoordinatorAgent.coordinate(task)
    |
    v
_classify(task, context) ──> SkillRegistry.classify(text)
    |                           • lowercase task + context
    |                           • +2.0 per keyword hit per category
    |                           • normalize to weights, sort desc
    |                           • {"general": 1.0} fallback
    |
    v
_select_agents(categories) ──> match registered specialists by category
    |
    v
_delegate_and_collect ──> AgentFinding per specialist
    |
    v
EvidencePool ──> dedupe / rank / consolidated report
    |
    v
Coordinated result ──> Supervisor synthesis
```

### Dependency graph

`CoordinatorAgent` now depends on the `SkillRegistry` abstraction instead
of a module-level constant. The registry, in turn, depends only on
`SpecialistAgent` (for typing) and knows nothing about concrete agent
implementations — agents are resolved lazily from their import paths.

### Backward compatibility

- `CoordinatorAgent()` with **no arguments** still works; it builds a
  registry seeded with `CATEGORY_KEYWORDS` as fallback keywords,
  preserving legacy classification results exactly.
- `CATEGORY_KEYWORDS` remains in `coordinator.py` as the fallback source.
- `_classify()`, `_select_agents()`, `register_specialist()`, and
  `register_specialists()` retain their original signatures and behavior.
- YAML-registered keywords take precedence; fallback keywords apply only
  where no definition exists.

### Two registry systems (not to be confused)

| | `skills_engine/` | Agent Skill Registry |
|---|---|---|
| Concern | Knowledge injection (content packs) | Agent routing / dispatch |
| Source | `SKILL.md` + YAML frontmatter | `skills/agent_skills.yaml` |
| Output | Ranked knowledge injected into prompts | Category scores + selected agents |

See `docs/AGENT_SKILL_REGISTRY.md` for the full architecture document.

## 6. Migration notes

v0.4.0 is **fully backward compatible** — no breaking changes.

- **Existing code:** Any code that constructs `CoordinatorAgent()` or
  calls `_classify` / `register_specialist` continues to work unchanged.
- **Existing specialists:** Specialists registered via
  `register_specialist(s)` are automatically adopted into the registry
  by `register_agent`, so no extra setup is required.
- **Moving to YAML-driven routing (optional):** Load the central file and
  pass it to the coordinator:
  ```python
  from agents.team.coordinator import CoordinatorAgent
  from agents.team.skill_registry import load_skill_registry

  coordinator = CoordinatorAgent(skill_registry=load_skill_registry())
  ```
- **Editing keywords:** Update `skills/agent_skills.yaml` instead of
  editing source. Keep `CATEGORY_KEYWORDS` in sync only if you rely on
  the legacy fallback path.
- **Disabling a skill:** Set `enabled: false` in the YAML (or call
  `set_enabled(category, False)`) to exclude it from routing.
- **Prompts remain unwired:** `prompts/*_expert.md` are referenced by the
  registry's `prompt` field for documentation/metadata; they are not yet
  injected at runtime.

## 7. Example: adding a new specialist agent

### 1. Create the agent class

`agents/team/specialists/network_agent.py`:

```python
from agents.team.specialists import SpecialistAgent
from agents.team.evidence import AgentFinding

class NetworkSecurityAgent(SpecialistAgent):
    name = "network_security_agent"
    category = "network"
    capabilities = ["dns_analysis", "tcp_analysis", "tunneling_detection"]

    async def analyze(self, task, context=None) -> AgentFinding:
        findings = []
        evidence = []
        if "dns" in task.lower():
            findings.append("DNS query analysis performed")
            evidence.append("DNS traffic pattern recorded")
        return AgentFinding(
            agent_name=self.name,
            findings=findings,
            evidence=evidence,
            confidence=0.7,
            tools_used=["tcpdump"],
            category=self.category,
        )
```

### 2. Create the expert prompt

`prompts/network_expert.md` — follow the existing `*_expert.md` format.

### 3. Register the skill in `skills/agent_skills.yaml`

```yaml
- name: network
  category: network
  agent: "agents.team.specialists.network_agent:NetworkSecurityAgent"
  prompt: "prompts/network_expert.md"
  keywords: [network, dns, tcp, packet, pcap, tunnel]
  capabilities:
    - dns_analysis
    - tcp_analysis
    - tunneling_detection
  version: "1.0"
  enabled: true
```

### 4. Register at runtime

```python
from agents.team.coordinator import CoordinatorAgent
from agents.team.skill_registry import load_skill_registry
from agents.team.specialists.network_agent import NetworkSecurityAgent

coordinator = CoordinatorAgent(skill_registry=load_skill_registry())
coordinator.register_specialists([NetworkSecurityAgent()])
```

### 5. Test

```bash
python -m pytest tests/test_agent_skill_registry.py -v
```

The new category is now routable: a task containing any `network`
keyword will classify toward the `network` category and dispatch
`NetworkSecurityAgent` automatically.
